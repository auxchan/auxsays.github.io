release_summary: "Starting December 1, 2026, we’re migrating notifications on GitHub.com over the course of a week to make\
  \ subscriptions more predictable, correct unexpected behavior, and support the growing scale of activity.\n\n\n During the\
  \ rollout, notifications may behave differently for different users. No action is required, but the changes below may affect\
  \ how you manage and filter notifications. This does not apply to GitHub Enterprise Server.\n\n\n What is changing\n\n Routine\
  \ activity won’t resubscribe you: Previously, after manually unsubscribing, notification activities such as commenting,\
  \ submitting a pull request review, changing a thread’s state, or merge queue activity resulted in a re-subscription. Now,\
  \ those actions leave you unsubscribed. Being mentioned, assigned, or receiving a pull request review request will continue\
  \ to resubscribe you since those actions ask for your attention.\n\n\n Team-mention notifications will reflect current team\
  \ membership and mentions: Previously, you could continue receiving notifications after a team mention was removed or you\
  \ left the team. If you joined a team after it was mentioned, you wouldn’t receive notifications for future activity. Now,\
  \ removing the mention or leaving the team stops future notifications based on that team mention, so you may receive fewer\
  \ notifications. Joining the team enables notifications for future activity on threads where it was already mentioned. Other\
  \ reasons, such as commenting, may still result in notifications.\n\n\n\n\n Removing a mention won’t stop notifications\
  \ you receive for other reasons: Previously, removing a mention could stop notifications even if you’d also participated\
  \ in another way. Now, if someone removes a mention, you’ll stay subscribed as long as another reason, such as commenting\
  \ or being assigned, still applies.\n\n\n\n\n The Subscriptions page will show only subscriptions you added manually : The\
  \ Subscriptions page will only list threads you explicitly subscribed to, not threads you get notifications for because\
  \ you authored, commented, were assigned, were mentioned, or were asked to review. To manage those notifications and bulk-unsubscribe,\
  \ use your notification inbox .\n\n\n\n\n Notification reasons will follow a consistent priority: The reason shown in your\
  \ inbox and email footer is now based on priority instead of the most recent activity. The order is mention, team mention,\
  \ assign, review requested, comment, manual, author, state change, and subscribed. For issues, assign has the highest priority.\
  \ If you filter or automate based on notification reasons, review those rules, since the reason shown may change.\n\n\n\n\
  \n Email headers will include all notification reasons: Notification email headers will include all applicable notification\
  \ reasons, such as “mention” and “subscribed”, helping you better filter notifications. If you use filters or automations\
  \ based on these notification reasons, please review them as they will now include all notification reasons.\n\n\n\n\n Team\
  \ mentions in security advisory comments will show a “team mention” reason: If your team is @mentioned in a comment on a\
  \ repository security advisory, the notification will say “team mention” instead of “commented”.\n\n\n\n\n Other notification\
  \ behaviors, such as notification settings, watched repositories, custom thread subscriptions, and previously delivered\
  \ notifications remain unchanged.\n\n\n Join the discussion in GitHub Community .\n\n\n\n The post More predictable notifications\
  \ on GitHub.com appeared first on The GitHub Blog ."
